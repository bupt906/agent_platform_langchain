# 在新智能体中调用知识库

面向要开发新 Agent 或 Skill、需要用到企业知识库的人。

知识库检索是平台的**公共能力**：五个工具已经注册在全局工具表里，你不需要写客户端、
不需要拿密钥、也不需要知道背后是万悟平台还是知识库中台。换后端时你的代码一行都不用改。

---

## 30 秒上手

按你要做的东西选一条路：

| 你在写什么 | 怎么接 |
| --- | --- |
| 声明式 Skill（`SKILL.md`） | frontmatter 里加一行 `tools: [search_knowledge]` |
| Python Agent（`agents/` 下的类） | `registry.get_many(["search_knowledge"])` |
| 确定性流水线（不走模型自主决策） | `deps.knowledge.search(...)` |

---

## 可用工具

| 工具 | 用途 | 何时用 |
| --- | --- | --- |
| `search_knowledge` | 检索并返回原文证据片段 | **默认选它**。要自己综合多条证据下判断时 |
| `answer_from_knowledge` | 知识库直接作答，带来源 | 一步能答完的事实性问题 |
| `list_knowledge_bases` | 列出可检索的知识库及 ID | 不确定该查哪个库时先调它 |
| `fetch_knowledge_document` | 按原文顺序取回某文档全文 | 要通读整篇，而不是若干片段 |
| `add_to_knowledge_base` | 把文本写入知识库 | 沉淀产出。**有副作用**，仅在用户明确要求保存时调用 |

### 参数

```python
search_knowledge(query: str, kb_ids: str = "", top_k: int = 5)
answer_from_knowledge(question: str, kb_ids: str = "")
list_knowledge_bases()
fetch_knowledge_document(doc_id: str)
add_to_knowledge_base(kb_id: str, filename: str, content: str)
```

`kb_ids` 是**逗号分隔的字符串**（方便模型填写），留空表示检索全部可访问的知识库。

## 方式一：声明式 Skill

在 `src/agent_platform/skills/<你的skill>/SKILL.md` 的 frontmatter 里声明工具名即可：

```markdown
---
name: equipment-fault-analysis
description: >-
  依据企业知识库中的设备手册与检修规程，分析设备故障现象、定位可能原因并给出处置建议。
  当用户描述设备异常、报警代码或检修问题时使用。
tools: [search_knowledge, fetch_knowledge_document, write_file]
---

# 设备故障分析

## 工作方式

1. 先用 `search_knowledge` 检索故障现象相关的手册条文和历史案例。
2. 证据不足时换关键词再检索一次；仍不足就明说缺什么，不要靠常识补。
3. 需要完整规程时用 `fetch_knowledge_document` 取回全文。
4. 输出结论时逐条标注依据来自哪个文件。

## 证据规则

- 只依据检索到的原文下判断，不引入知识库之外的经验。
- 工具返回「知识库检索失败」时，说明这次没查成，**不要**当作「知识库里没有」继续下结论。
- 工具提示「检索能力不完整」时，说明结论可能不全面。
```

平台启动时 `resolve_skill_tools` 会校验工具名。写错了该 Skill 会被隔离并在日志里告警，
不会带着坏配置上线。

## 方式二：Python Agent

```python
from agent_platform.agents.base import BaseSkill
from agent_platform.tools import registry


class EquipmentAgent(BaseSkill):
    @property
    def name(self) -> str:
        return "equipment_fault"

    def create_agent(self, model_provider, checkpointer=None):
        model = model_provider.get_model()
        tools = registry.get_many(["search_knowledge", "fetch_knowledge_document"])
        return create_agent(model, tools, system_prompt=SYSTEM_PROMPT, checkpointer=checkpointer)
```

## 方式三：确定性流水线

不想让模型自己决定何时检索时（例如逐句核验），直接用 provider：

```python
async def check(sentence: str, kb_ids: list[str], deps) -> dict:
    result = await deps.knowledge.search(kb_ids, sentence, top_k=5)

    if not result.is_complete:
        # 后端有降级，命中可能不全——别把这次结果当作定论
        logger.warning("检索能力不完整: %s", result.degraded)

    for hit in result.hits:
        print(hit.kb_file, hit.relevance, hit.content)
```

`deps.knowledge` 的类型是 `KnowledgeProvider` 接口，不是某个具体实现。方法签名见
[`knowledge/provider.py`](../src/agent_platform/knowledge/provider.py)。

异常分两类，含义不同：

```python
from agent_platform.knowledge import KnowledgeConfigError, KnowledgeUnavailable

try:
    result = await deps.knowledge.search(kb_ids, query)
except KnowledgeConfigError:
    ...  # 配置问题：密钥无效、知识库 ID 不存在。重试无意义，要让人看见
except KnowledgeUnavailable:
    ...  # 后端暂时不可用。可重试或降级
```

---

## 一条必须守住的语义

**「检索失败」和「知识库里没有」是两件事。**

工具在这两种情况下返回的文本是刻意区分开的：

| 情况 | 工具返回 |
| --- | --- |
| 知识库里确实没有 | `未检索到相关内容。` |
| 这次没查成 | `知识库检索失败：<原因>\n这不表示知识库中没有相关内容，请不要据此下结论。` |
| 查到了但后端不全 | 证据 + `⚠️ 本次检索能力不完整，以下后端不可用：milvus。…` |

写 prompt 时要把这条规则传达给模型。在文档审阅这类场景，把「没查成」当成「无问题」
会直接产出错误结论——这是整个设计里最容易出事的地方。

参考写法：

```text
- 工具返回「未检索到相关内容」时，说明知识库中没有依据，据此判断。
- 工具返回「检索失败」时，说明本次检索未完成，应告知用户而不是下结论。
- 工具提示「检索能力不完整」时，结论中要说明可能存在遗漏。
```

## 写入知识库

`add_to_knowledge_base` 有副作用，且**写入不等于立刻可检索**：

```text
《设备故障总结.md》已写入知识库并进入解析队列，解析完成后即可检索。文档 ID：xxx
```

内容扫描判定为高风险时会转人工审核，此时返回：

```text
《敏感.md》已提交到知识库，但需要管理员在入库审核中放行后才能被检索（内容风险等级：high）。文档 ID：xxx
```

模型看到后一种时不能说「已入库，可以检索了」。prompt 里最好显式交代这一点。

## 后端与配置

`KNOWLEDGE_PROVIDER` 决定由谁提供能力，你的代码不受影响：

| 取值 | 后端 | 需要的配置 |
| --- | --- | --- |
| `wanwu` | 万悟平台 hit 接口 | `KB_API_BASE_URL`、`KB_API_KEY` 等 `KB_*` |
| `omnimind` | 知识库中台服务契约层 | `OMNIMIND_BASE_URL`、`OMNIMIND_API_KEY`，需装 `kb-sdk` |
| `dual` | 两者并行，用 omnimind 结果并记录差异 | 两组都要 |

不同后端的能力有差异，工具会如实说明而不是编造：

| 能力 | wanwu | omnimind |
| --- | --- | --- |
| `search_knowledge` | ✅ | ✅ |
| `list_knowledge_bases` | ❌ 返回「不提供知识库清单」 | ✅ |
| `answer_from_knowledge` | ❌ 返回「不支持服务端问答」 | ✅ |
| `fetch_knowledge_document` | ❌ | ✅ |
| `add_to_knowledge_base` | ❌ | ✅ |

所以：**要用检索之外的能力，后端得是 `omnimind`。**

## 迁移到知识库中台

现网默认仍是 `wanwu`。切换按下面的顺序做，每一步都可回退。

### 前置条件

1. **内容就位。** 知识库中台里要有对应的文档。审阅用的行业标准目前只在万悟，
   没搬过去之前切换会导致检索不到依据。用中台前端上传，或用 `add_to_knowledge_base` 灌入。
2. **拿到服务密钥。** 知识库中台 `.env.production` 里的 `SERVICE_API_KEY`。
3. **装 SDK。**

   ```bash
   cd <知识库中台仓库>/sdk && python -m build
   pip install <知识库中台仓库>/sdk/dist/kb_sdk-1.0.0-py3-none-any.whl
   # 或开发期直接：pip install -e ".[omnimind]"
   ```

### 第一步：配好但不启用

`.env` 里填上连接信息，`KNOWLEDGE_PROVIDER` 先不动：

```bash
OMNIMIND_BASE_URL=http://<知识库中台>:8000
OMNIMIND_API_KEY=<中台的 SERVICE_API_KEY>
OMNIMIND_TOP_K=5
```

验证连通性：

```bash
curl -H "X-Service-Key: $OMNIMIND_API_KEY" http://<知识库中台>:8000/api/v1/service/health
```

### 第二步：配置 kb_id 映射（如果有外部调用方）

审阅任务由外部系统下发，它传的 `kb_ids` 是万悟的数字串（如 `2003716670903816192`），
而中台用 UUID。先查出中台对应知识库的 ID：

```bash
curl -H "X-Service-Key: $KEY" http://<知识库中台>:8000/api/v1/service/kbs
```

然后配映射：

```bash
OMNIMIND_KB_ID_MAP=2003716670903816192:b79aa131-f8d0-44c8-b2b1-0b40ccd8c7c7
```

没配映射的旧格式 ID 会被明确拒绝并提示该补什么，不会静默发到中台换回一个
语焉不详的 403。

> 注意：切换后回调给下游的 `reference.kb_id` 会从数字串变成 UUID。
> 下游若对这个字段有格式假设，需要同步确认。

### 第三步：双跑观察

```bash
KNOWLEDGE_PROVIDER=dual
```

两个后端都查，**返回中台的结果**，把差异写进日志：

```text
知识库双跑 | query=风机振动超标 | 主(omnimind)=5 条/2 文件 | 影子(wanwu)=4 条/3 文件 | 文件重合=2/3 | 主降级=无
```

影子后端挂了不影响调用方；主后端挂了会照常报错——不会拿影子结果掩盖中台的真实可用性。

跑一批真实任务，看：
- 文件重合度是否可接受；
- 审阅结果的 `issues_found` 数量是否有异常波动；
- 有没有持续出现的 `主降级=[...]`。

也可以用中台自带的离线评测：

```bash
curl -X POST http://<知识库中台>:8000/api/v1/evaluation/retrieval \
  -H "X-Tenant-ID: $TENANT" -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"question":"风机振动超标","expected_asset_ids":["<应该命中的文档ID>"]}'
```

返回 recall / MRR / nDCG。

### 第四步：切换

```bash
KNOWLEDGE_PROVIDER=omnimind
```

重启后端。观察一段时间无异常后，可以删掉 `.env` 里的 `KB_*` 配置。

### 回退

把 `KNOWLEDGE_PROVIDER` 改回 `wanwu` 并重启即可，没有数据迁移需要回滚。

## 排查

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| Skill 启动时被隔离，日志报「工具未注册」 | 工具名拼错，或 provider 构造晚于工具注册 | 核对 `SKILL.md` 里的名字；lifespan 中 provider 必须先于 `register_all_declarative_tools` |
| 工具返回「知识库服务层未就绪」 | 中台没配 `SERVICE_API_KEY`，或服务账号没建 | 中台补配置后重跑 `bootstrap` |
| 工具返回「不是知识库中台的 UUID」 | 传了旧平台的知识库 ID | 配 `OMNIMIND_KB_ID_MAP` |
| 检索总是带 `检索能力不完整` | 中台的 ES / Milvus / 推理服务有问题 | 查中台 `docker compose ps` 与各服务健康状态 |
| `ModuleNotFoundError: kb_sdk` | 后端设成 omnimind 但没装 SDK | `pip install -e ".[omnimind]"` |
